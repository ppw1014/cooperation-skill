# 保守档附录(Implementer 为较弱或易偏离的模型时叠加)

> 适用:部署配置里某个 Implementer 的档位登记为**保守**(protocol §1.3)。本附录**覆盖**正文中与该 Implementer 相关的对应条款;没提到的照正文。
> 何时用:Implementer 读不稳大代码库、容易把推断当事实、容易越过范围顺手改东西。判断不了时先按保守档跑两三张卡,交付质量稳定再改回标准档。
> 这些规则是给执行者兜底的,不是"更严谨的做法"。用在强模型身上只会拖慢它。

## 1. 黄区并入红区

protocol §6.1 的黄区事项(新增运行时依赖、调整本卡新引入的接口形状、CI 结构、卡面与仓库不符时的择一解释、相邻小功能)**一律 L1-停**:停在该点上报,等 Architect 裁决后再做。不使用 L1-提案。

**拿不准是不是红区,按红区处理。** L1 问一句的成本低于弱执行者按错误理解做完再返工。

## 2. 卡面由 Architect 写全

- **完成判据由 Architect 写到可执行**:具体输入、命令、预期结果。Implementer 不做判据细化,不创建细化文件;卡级门禁的第 2、3 项(protocol §2.3)直接对卡面判据核对与复跑;
- **接口契约写进卡面**:跨模块 / 跨进程 / 对外的接口给出签名、类型、命令参数,与 schema 逐字段对照后写入;
- **点名不做的事**:本卡明确不做什么、归属哪张后续卡,防扩范围;
- 确有必须隔离的区域时,可以给**文件范围**(允许改动的目录或文件);
- 卡面断言的事实必须由 Architect 核实过:数据源沿源文件 → 构建 → 运行时确认可达;第一次消费的基建实际 import 一次;要求的出口(日志、事件、接口)在当前架构里真有消费方;点名技术栈时枚举 companion 闭包并核查 peerDependencies。标准档里这些可以写进「已知未知」交给实现方核实,保守档不行。

## 3. 逐卡审核

交付先到 Architect 审核,通过后才进 Coordinator 的卡级门禁。审核看:

1. 目标与完成判据逐条有落点;
2. 改动面(`task_base..delivery_sha`)未越红区、未超文件范围;接口与卡面一致;
3. 自主决策逐项过目;
4. 此前的裁决按原文落地;
5. 明显隐患:错误路径、资源清理、平台差异、对范围外行为的回归风险;
6. 实施发现逐条定性。

打回一次给全,每条指得到卡面依据;最多两轮,仍不过则 Architect 接管重写(信道声明接管,不静默动手)。受 protocol §2.1 越线信号约束。

门禁退回照常直达 Implementer;Reviewer 逐卡验收的退回发给 Architect 定性后再转,不直达。

## 4. 体量预算

- 出卡时给**体量预算**(常规卡默认 ±500 行,项目可调);穷举覆盖型任务直接声明不设限;对抗档把恶意输入矩阵单独估;
- 计量口径:格式化工具处理后的源码行数;交付报告分组统计:手写代码 / 强制生成物 / fixture 数据 / 协作文档;
- **超预算不停工**,交付报告如实披露成因,是否重构由审核裁量。预算是发现跑偏的信号,不是停工触发器。

## 5. 完整交付报告与自检

交付报告用八节(批量交付按卡分节):

1. 做了什么:关键实现思路,不复述卡面;
2. 验证方法:完成判据逐条怎么验的;需要实机的写复现步骤;
3. 自主决策:每项一句理由;无则写"无";
4. 实施发现:L1(已裁决的引用信道编号)/ L2 / L3;无则写"无";
5. 存疑点:拿不准的地方如实列出,宁可多报;
6. 体量:分组统计,对照预算,超量说明成因;
7. 门禁:本地与 CI 分别说明,给出实际验证 SHA;没有 CI run 不写 CI 通过;
8. C / 托管任务的运行信息(同正文)。

交付前自检逐项打勾并写进报告:

- [ ] 完成判据逐条自测通过,写明每条怎么验的("应该没问题"不算验证);
- [ ] 测试面按卡面验收强度交付,常规档不堆恶意输入矩阵;
- [ ] 未越红区、未超文件范围(`git diff --stat` 看改动面);
- [ ] 项目门禁命令表全量本地全绿;
- [ ] 无 TODO / 注释掉的代码 / 调试打印残留。

## 6. 启动提示词

用 `templates/implementer-bootstrap.md` 时,在必读文档里加上本附录的项目内路径,并把"三条原则"的第 2 条换成:**红区与黄区的事一律停下上报,拿不准按红区处理**。
