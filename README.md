# cooperation-skill

**多 agent 协作框架** —— 一个 agent 出任务卡与契约,另一个按卡实现,第三个(可选)做交叉评审;人类只做决策与触发,不搬运内容。

这不是"让两个 AI 一起干活"的泛泛建议,而是一套**从真实翻车里长出来的硬约束**:每一条规则背后都有一次具体的代价。框架本身可以照抄,但真正值钱的是 [`anti-patterns.md`](anti-patterns.md) 里那些"为什么必须这么规定"。

## 它解决什么问题

多 agent 协作最常见的失败不是"AI 写不出代码",而是这四类:

| 失败 | 这里的对策 |
| --- | --- |
| 实现方发现了更好的做法,**直接就改了** | 铁律:裁决之前一律按契约实现。**发现 ≠ 授权**,发现的价值在进入裁决流程 |
| 出卡方写了个**不存在的数据源 / 没法验的验收标准**,实现期才炸 | 出卡门禁 13 条 + 开工前交叉 review;定性时先查是不是出卡侧的锅,不冤枉实现者 |
| review 停不下来,**一张小卡审了 7 轮**,体量做到预算 2.3 倍 | 一轮止损 + 必审四类 + 不审清单 + 四个越线信号;验收强度由"面对谁"决定,不由"多重要"决定 |
| 两个 agent 共享工作区,一次 `git checkout` **抹掉对方未提交的活** | 工作区形态 A/B 分别定纪律;形态 A 下切分支/merge 前必须确认对方无现场 |

## 角色

```
Owner(人类)     方向决策、产品验收、真机测试、花钱的事
                 └─ 只触发,零内容搬运

Architect        出任务卡、定接口契约、裁决、终审验收、merge
                 └─ 专属:契约制定权 · 裁决权 · merge 权

Implementer      按卡实现、自检、交付报告、上报实施发现
                 └─ 专属:绿区自主决策权

Reviewer(可选)  开工前评审文档与高风险卡面;交付后初审实现
                 └─ 有放行/打回权,但无契约修改权、无 merge 权
```

**Reviewer 是可选的**——只有两个 agent 的项目不部署它,职责全部回落 Architect,框架退化为双 agent 原形。可移植性是设计目标之一。

## 核心机制

| 机制 | 一句话 |
| --- | --- |
| **信道** | 仓库内只追加的 markdown 文件;编号严格递增;`git add` = 已读回执。三方部署时换成消息内 `已读至:#N` 水位线(staging 是全局状态,表达不了"谁读了") |
| **L1 / L2 / L3** | L1 阻塞立即停工上报;L2 缺陷继续按契约做、随交付报告结构化提出;L3 建议**裁决前不得实现** |
| **绿区 / 红区** | 低风险"必然配套"决策下放实现侧(四条件全满足 + 披露审计);新增运行时依赖、公共契约变更、安全边界一律停工 |
| **一轮止损** | 开工前 review 一次性给全问题,不往返。出现"本轮问题多数由上一轮修订产生"立即收口 |
| **验收强度分档** | 判据是**"谁会攻击这段代码"**。只处理自家输入 = 常规档;处理外部/不可信输入 = 对抗档。给常规档做对抗验收会让体量翻倍且不增加安全性 |
| **体量披露制** | 出卡给预算(默认 ±500 行),预授权上限 = 预算 × 1.3。**超预算不停工**,如实披露即可——预算是披露口径,不是停工触发器 |
| **打回判据** | Reviewer 的打回项**必须能指到卡面某一行**。指不到就是卡面的问题,走 Architect 裁决;实现方有权拒绝无依据的打回 |
| **轮次封顶** | 初审 ≤2 轮 → 升级;终审 ≤2 轮 → 接管重写。一张卡打回总轮次封顶 4 |

## 在新项目部署

关键认知:**其他 agent 读不到你的 skill 目录**——它们只读项目仓库和自己的启动提示词。所以部署 = 把协作基础设施**实例化进目标项目的仓库**;本仓是母本 + 部署器。

1. **定角色数** —— 两个 agent 走双角色原形,三个则加 Reviewer;
2. **定配置** —— 信道路径、分支约定、**项目门禁命令表**(protocol §8 的坑位)、体量预算基线;
3. **定工作区形态** —— A 还是 B(见下),形态决定 git 纪律;
4. **实例化** —— 把 `protocol.md` / `implementer.md` / `anti-patterns.md`(三方再加 `reviewer.md`)拷进项目 `docs/collab/`,**填掉全部【坑位】**;
5. **出启动提示词** —— 按 `templates/*-bootstrap.md` 填空交给 Owner,只指路径不复制内容;
6. **写信道首条部署宣告** → 建 backlog → 出第一张卡。

完整步骤见 [`SKILL.md`](SKILL.md)。

## 工作区形态 A / B

| | 形态 A:共享本地工作区 | 形态 B:分离工作区 |
| --- | --- | --- |
| 可见性 | 未提交变更互相可见,写入即送达 | 一切经 commit + push 才可见 |
| 第一铁律 | 切分支 / merge 前**必须确认对方无未提交现场** | 远端分支是唯一事实,本地状态不作数 |
| 信道 | 消息写入文件即送达 | 消息必须 push 后才算送达,读前先 pull |

形态由 Owner 指定;**未指定时两个 agent 可以自己探测**——Architect 在信道写一条带随机标记的消息但**不 commit**,对方读得到就是 A,读不到则补 push 走通就是 B(补推过程本身完成了 B 形态的通路验证)。

## 出处与成色

源自三个真实项目的协作实践与复盘,项目名已匿名化为**项目 A** / **项目 B** / **项目 C**:

- 项目 A 贡献了主体协议(v1.5)与出卡侧、实现侧、验收侧的绝大部分反模式;
- 项目 B 贡献了交叉 review 的止损规则与验收强度分档——**代价是一张本地文档检查脚本的卡走了 7 轮 review、体量做到预算 2.3 倍**;
- 项目 C 是第一个跑三方部署(Architect 与 Reviewer 异源)的项目,贡献了形态 A 下的写入点纪律与提交 pathspec 纪律,以及**门槛落点、区分性输入、接口消费方**三条出卡门禁——全部来自一张高风险卡的预审实战。

**成色说明**:`anti-patterns.md` 里带「源案例」的条目来自实战。「三方协作」一节的六条**原为机制推演,现已有一例实战校准**(项目 C 首张三方高风险卡:预审一轮提出 5 项硬意见,核实后全部成立,其中两项比预审描述更严重),文件内已记录该案例;六条本身尚未逐条被实战检验,用的时候仍请按这个区别对待——这套框架自己的规矩就是:没验证过的断言不能当事实用。

## 反馈回流

新项目撞出的教训**先落项目实例文档,再回流本母本**——母本是跨项目资产,实例是项目现场。两处都改时先实例后母本,防漂移。
